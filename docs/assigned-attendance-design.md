### 実装で採用した細部

新規指定の対象は有効な部員とし、役職では絞らない。無効化・削除済みの既存指定は保持し、部員が削除された場合は指定時の名前を表示する。
更新APIの安全上限は1要求300件。表示順は学籍番号とする。
当日の出席確認は新方式では表示せず、書き込みAPIも拒否する。指定変更の即時Push・Discord通知は追加しない。

指定者情報は詳細を開くときに専用APIから取得する。`canManage`はNext.jsがセッションから判定し、キャッシュしない。
そのため、案に挙げた予定一覧への人数・revisionの追加や、カードへの所有者props追加は行っていない。
カレンダーのローカルキャッシュはv2へ変更し、参加者指定の期限を空のまま保持する。

編集UIは既存の`AppModal`内で一覧と選択画面を切り替える。モーダルを重ねず、参加者の保存成功時に閉じる。
失敗時は選択を保持し、競合時は再取得するまで保存を無効にする。

新規予定作成の通信切断後の再送は、既存のランダムID発行方式のまま。安定IDによる冪等な作成は今回の実装には含めない。
同じ`eventId`を明示して既存予定へ再作成を要求した場合は409で拒否し、上書きしない。

## 1. 確定した仕様

| 項目 | 仕様 |
| --- | --- |
| 新しい出欠方式 | 参加者指定 |
| 参加者の指定・変更 | 予定の作成者のみ |
| 指定対象 | 役職による制限なし。部員・部長・副部長・会計・仮入部・OB・OGを区別しない |
| 0人の予定 | 保存可能。後から作成者が参加者を追加できる |
| 本人の操作 | 参加登録・辞退・欠席・遅刻・早退・中抜けの連絡は不要。対応する操作を設けない |
| 公開範囲 | 予定と指定参加者の名前は、ログイン利用者全員が閲覧可能 |
| Discord当日通知 | 指定参加者全員を掲載 |
| 出欠方式の変更 | 作成後は不可。「全員参加」「希望者参加」を含む全方式に適用 |
| 日程調整 | 今回の対象外。Issue #216とその設計書は変更しない |

新規作成画面では保存前まで出欠方式を切り替えられる。保存後も日時・場所・説明などは編集できる。
作成者限定にするのは参加者の指定・変更であり、既存予定の一般情報の編集・削除権限まで一律に変更する要件ではない。
作成者の変更・権限委譲、方式変更後の復元、参加者への個別通知は今回実装しない。

## 2. 既存実装との違い

### 2.1 3種類のデータを混ぜない

| データ | 意味 | 参加者指定での扱い |
| --- | --- | --- |
| `absences`の`type = 出席` | 希望者参加への本人の参加登録 | 作成・更新しない |
| `absences`の欠席・遅刻等 | 本人の出欠連絡 | 作成・更新・本人削除のAPIを拒否 |
| `event_attendance` | 当日の出席確認 | 指定時に自動登録しない |
| 新規`scheduled_participants` | 作成者が指定した参加者 | 参加者表示と当日通知の正本とする |

現在の`event_attendance`は取得・更新時にOB・OGを除外する。ここを指定参加者の保存先に流用すると、今回の仕様に反する。
当日の出席確認機能を参加者指定にも表示するかは未合意のため、初期案ではこの方式の確認UIを非表示にする。既存2方式の確認機能は維持する。

### 2.2 現在の二択分岐は三択へ変更する

`normalizeScheduleAttendanceMode`は現在`ATTENDANCE`以外を`ABSENCE`へ変換している。
`ScheduleCard`とDiscordの日次集計にも「希望者参加以外は欠席者」とする分岐がある。
新しい値を追加するだけでは、参加者指定が全員参加として扱われるため、各分岐を明示的な三択にする。

既存の予定取得レスポンスには`CREATED_BY`がある。所有者を新しく自由入力させる必要はない。
Workerの既存予定更新は`attendance_mode`を毎回書き換えているため、一般項目だけの更新に変更する。

## 3. 型・既存フィールドの変更

### 3.1 出欠方式

```ts
type ScheduleAttendanceMode = "ABSENCE" | "ATTENDANCE" | "ASSIGNED";
```

| 値 | 表示名 | 回答データ | 表示する一覧 |
| --- | --- | --- | --- |
| `ABSENCE` | 全員参加 | 欠席・遅刻・早退・中抜け | 欠席者等 |
| `ATTENDANCE` | 希望者参加 | 本人の参加登録 | 参加者 |
| `ASSIGNED` | 参加者指定 | 作成者による指定 | 指定参加者 |

読み取り時の既存の空値は互換性のため全員参加として扱う。書き込みでは上記3値以外を400で拒否し、未知の値を黙って全員参加に変換しない。
既存の不正値があれば移行前に件数を調べ、勝手な一括修正はしない。

### 3.2 `schedules`の既存項目

| 項目 | 変更内容 |
| --- | --- |
| `attendance_mode` | `ASSIGNED`を許可。作成後は変更不可 |
| `created_by` | 既存値を所有者判定に使用。新規は認証済み本人の学籍番号をサーバーで設定し、以後変更不可 |
| `attendance_deadline` | `ASSIGNED`はnull。入力・表示・期限判定を行わない |
| `updated_by` / `updated_at` | 指定参加者変更時にも、実行した作成者と変更時刻を更新 |
| その他 | 日付・終了日・開始終了時刻・タイトル・場所・説明・色などは既存仕様を維持 |

`toScheduleResponse`は現在、期限がnullでも開催日を補完する。`ASSIGNED`では補完せず、`ATTENDANCE_DEADLINE`を空文字で返す。
日時は新しい参加者テーブルでも既存の`JST_SQL_TIMESTAMP`による保存形式に合わせる。

## 4. 追加するDBフィールド

### 4.1 `schedules.participants_revision`

| 項目 | 型 | NULL | 既定値 | 用途 |
| --- | --- | --- | --- | --- |
| `participants_revision` | INTEGER | 不可 | 0 | 指定参加者の編集競合を検出する連番。0人でも保持する |

参加者集合が変わった場合のみ1増やす。同じ集合の再送は増やさない。
作成時は参加者の有無によらず0、以後の追加・解除で増やす案。
一般の予定情報の編集とは別の連番とし、タイトル変更だけで参加者編集を競合扱いにしない。

### 4.2 新規`scheduled_participants`

| カラム | 型 | NULL | 内容・値の決定元 |
| --- | --- | --- | --- |
| `event_id` | TEXT | 不可 | 対象の`schedules.id`。予定への外部キー |
| `student_number` | TEXT | 不可 | 指定された部員の学籍番号。既存規則で正規化 |
| `display_name_snapshot` | TEXT | 不可 | 指定時の表示名。サーバーで部員情報から決定 |
| `assigned_by` | TEXT | 不可 | 指定した本人の学籍番号。作成者と一致 |
| `assigned_at` | TEXT | 不可 | 指定日時。サーバーが生成 |

主キーは`(event_id, student_number)`。同じ人を同じ予定に複数回指定できない。
`student_number`へ索引を追加し、参加予定の検索や将来の部員管理に使う。
予定削除では指定情報も削除する。部員の削除・無効化では、指定情報を自動的に消さない案。
表示名は現在のニックネーム・氏名を既存の表示規則で解決し、部員情報が取得できない場合にsnapshotを使う。メールアドレスは保存・公開しない。
部員への削除CASCADEは設定しない。`assigned_by`も履歴を残すため文字列として保持する。

概略DDL（まだ実行しない）:

```sql
ALTER TABLE schedules
ADD COLUMN participants_revision INTEGER NOT NULL DEFAULT 0
CHECK (participants_revision >= 0);

CREATE TABLE scheduled_participants (
  event_id TEXT NOT NULL REFERENCES schedules(id) ON DELETE CASCADE,
  student_number TEXT NOT NULL,
  display_name_snapshot TEXT NOT NULL,
  assigned_by TEXT NOT NULL,
  assigned_at TEXT NOT NULL,
  PRIMARY KEY (event_id, student_number)
);

CREATE INDEX idx_scheduled_participants_student_number
ON scheduled_participants(student_number);
```

解除時は対応する行を削除する。残す人の`assigned_by`・`assigned_at`は変更しない。解除後に再指定した場合は新たな指定日時を保存する。
全変更の監査履歴テーブルや解除済み行の保持は初期対象外。将来の方式変更時の復元とは別要件である。

### 4.3 追加しない項目

- 回答状態・参加承認状態・欠席理由・本人の承認日時: 本人の回答を求めないため不要。
- 参加者数のDBカラム: 対応する行数から計算する。
- 選択可能ロール・公開範囲: 今回は固定仕様なので設定項目にしない。
- 別の所有者ID: 既存の`created_by`を利用する。
- 方式の履歴・復元用状態: 今回は方式変更不可。指定情報は独立テーブルに置くが、復元機能は作らない。

## 5. 画面とAPIに追加するフィールド

### 5.1 新規予定作成

| 入力 | 型 | 必須条件 | 検証 |
| --- | --- | --- | --- |
| `attendanceMode` | enum | 新しいUIでは必須 | 3値のいずれか。既存クライアントの省略時は従来どおり`ABSENCE` |
| `assignedStudentNumbers` | string[] | `ASSIGNED`の場合は必須 | 空配列可。本人IDの書式と存在を確認。重複は正規化して除去 |
| 既存の予定情報 | 既存型 | 既存仕様 | 開始・終了時刻を含めて既存検証を維持 |

非`ASSIGNED`で指定配列を受け取った場合は400とする。画面の方式切り替え時は不要なフィールドを送らない。
`ASSIGNED`で非空の`attendanceDeadline`が送られた場合も400。予定と指定参加者は同じDB処理で作成する。
参加者の氏名・所有者・指定者・時刻はクライアントから受け取らない。
存在しないIDを黙って除外して成功扱いにせず、全体を入力エラーにする。

選択UIは検索付きチェックボックス一覧、選択済み人数、選択解除を用意する。役職のフィルターで選択不可にはしない。
検索語・選択中ID・保存中フラグは画面の一時状態であり、DB項目ではない。

### 5.2 参加者一覧の取得と編集

専用API案: `GET /api/schedule-participants?eventId=...`、`PUT /api/schedule-participants`。
Workerには同じ用途の読み取り・更新経路を追加する。

PUT入力:

```ts
type UpdateAssignedParticipants = {
  eventId: string;
  studentNumbers: string[];
  expectedRevision: number;
};
```

返却内容:

```ts
type AssignedParticipant = {
  studentNumber: string;
  displayName: string;
};

type AssignedParticipantsData = {
  eventId: string;
  revision: number;
  participants: AssignedParticipant[];
  count: number;
  canManage: boolean;
};
```

`canManage`は現在の認証主体と`created_by`の比較結果。共有キャッシュへ保存せず、Next.jsで要求ごとに付与する。
学籍番号は選択・照合用であり、画面の公開表示は名前だけを基本とする。部員プロフィール全体を返さない。
`assigned_by`・`assigned_at`は初期UIには不要なので、一般閲覧APIでは公開しない。

新しい予定レスポンスには`PARTICIPANTS_REVISION`と`ASSIGNED_PARTICIPANT_COUNT`を追加する案。
UIに必要な場合だけ人数を一覧で取得し、指定名の一覧は詳細で取得する。各予定ごとの追加SQLを繰り返さず、一括集計する。
カレンダーとホームの`ScheduleCard`へ`createdBy`を渡し、必要に応じて`assignedParticipantCount`も渡す。
共有型・UI props・クライアントキャッシュの復元型を一緒に更新する。

### 5.3 既存予定編集

編集画面の出欠方式は、選択肢を削除して変更不可の表示に置き換える。
更新APIでは`attendanceMode`省略は現在値を維持し、同じ値は互換性のため受理、異なる値は409で拒否する。
`createdBy`による所有者変更も拒否する。`updatedBy`は認証主体からサーバーで上書きする。
参加者変更は専用APIからのみ行う。既存の一般編集APIに指定配列が含まれていた場合は400を返す。
次回部会のupsert経路など、別経路のUPDATEでも方式を書き換えないよう確認する。

## 6. サーバーで権限・方式・競合を検証する

| 操作 | 許可条件 |
| --- | --- |
| 予定と指定参加者の閲覧 | ログイン済み。指定されている必要はない |
| 新規予定作成 | 既存の作成権限を維持。作成者はサーバーで記録 |
| 指定参加者の変更 | ログイン本人が`created_by`と一致、方式が`ASSIGNED`、予定が存在 |
| 本人の参加・辞退・欠席等 | `ASSIGNED`では作成者本人も含めて拒否 |
| 作成後の方式変更 | すべての方式で拒否 |

Next.jsは既存のCSRFチェック後、セッションから本人の学籍番号を決める。Worker APIキーは接続元の認証であり、作成者照合の代わりにはならない。
WorkerでもDB上の所有者・方式と、信頼したサーバーが渡した実行者を照合する。
クライアント入力にある`actor`・`createdBy`・`assignedBy`をそのまま転送しない。未知の入力キーも検証する。

既存`/api/absence`のPOST・更新・DELETEとWorkerの`absences`関連経路に、`ASSIGNED`拒否を追加する。
古い画面、直接API呼び出し、期限前後の違いで制限を回避できないことを保証する。
予定が見つからない場合は404。認証なし401、他人による指定変更403、状態・revision競合409、入力不正400とする案。

参加者更新は現在集合と送信集合を比較し、追加と解除だけを反映する。
同じ集合の再送は、所有者・方式の確認後に成功として現在値を返せる。違う集合でrevisionが古い場合は409を返す。
DBでrevision確認、集合更新、revision加算、予定の更新者・更新日時更新を一体で実行する。
条件付きUPDATEが0件だった場合も後続の参加者変更が実行されない構造にする。事前SELECTだけで競合を防いだとみなさない。
D1のbatchでまとめる場合は、SQL失敗時に全体が戻ることと、条件不成立を成功扱いにしないことを実環境テストで確認する。

方式固定はWorkerの検証に加え、DBの変更禁止トリガーで守る案。空値の互換性と既存の次回部会処理を移行テストで確認してから採用する。
通常の更新で`attendance_mode`や`created_by`を不用意に再設定しない。

## 7. 表示・Discord・キャッシュを更新する

### 予定詳細とホーム

`ASSIGNED`では「指定参加者」と人数・名前を表示する。0人は「参加者は指定されていません」とする案。
本人向けの参加登録・取り消し・欠席連絡・期限表示は出さない。
作成者にだけ「参加者を編集」を表示し、既存の共通`AppModal`で選択する。0人への変更は確認後に保存する案。
保存成功時にモーダルを閉じ、失敗・競合時は入力を保持する。
一般の欠席連絡ページへ直接アクセスした場合も、この方式は回答対象外として扱う。
ホームの「本日の欠席者」へ指定参加者を混ぜない。指定名は予定カード・詳細から閲覧する。

### Discordの当日通知とBOT

`buildDailyAttendanceEmbeds`を3方式で分け、`ASSIGNED`は新テーブルから全指定者を取得する。
`absences`と新テーブルを無条件に同時JOINして行数を増やさず、方式別クエリか分離した集計で統合する。
既存2方式は従来どおりの集計にする。表示名は画面と同じ規則で解決する。
指定されたOB・OGも除外しない。0人でも予定のembedを出し、「参加者は指定されていません」と表示する案。
タイトルは「指定参加者一覧」、各人の値は「参加予定」とし、当日出席したことを示す「出席確認済み」とは表現しない。
多数の場合は既存のembed分割・メッセージ分割を使い、全員を掲載する。表示名の長さ・メンション等も既存の安全な処理を適用する。
同じ集計関数を使うBOTの出欠状況コマンドにも反映する。コマンド名や登録設定は変更不要。
既存の日付抽出・Cronの送信タイミング・複数日予定の通知範囲は変更しない。
通知後の参加者変更による自動再送は初期対象外の提案。BOTは実行時点の指定情報を表示する。

### キャッシュと通知

`CACHE_TAGS.scheduleParticipants`を追加し、指定変更時に該当データと`schedules`・`notifications`など実際の依存先を無効化する。
日次の指定者集計は新しい情報を参照し、期限付きの古い参加者キャッシュを通知へ流用しない。
カレンダーのクライアントキャッシュは形式バージョンを上げ、人数・方式・所有者・revisionを整合させる。
`Object.values()`による位置参照が残るため、既存レスポンスのキー順変更を避け、今回触る箇所は名前付き項目を使う。
指定変更だけで既存の予定更新Pushを送るかは未合意。初期案は自動Push・個別Discord通知を増やさず、予定更新履歴と当日通知へ反映する。

## 9. 移行・反映・復旧

1. 既存の方式値・作成者の空値・学籍番号の表記を調査する。作成者不明を現在の閲覧者に置き換えない。
2. テーブルとrevisionを追加する。既存の参加登録・当日確認から指定者を自動移行しない。
3. Workerに3方式と新APIを反映する。新テーブルがまだ存在しない状態では新SQLを有効化しない。
4. アプリを反映し、新方式の作成を有効にする。古いタブからの方式変更はAPIで拒否する。
5. 3方式それぞれの作成・編集・詳細・通知を確認する。実データの変更・本番テスト送信は承認後に行う。

既存2方式の予定はそのまま残る。ただし方式変更不可は既存予定にも適用する。
作成者不明の旧予定は指定者変更を許可しない。所有者補完は別途承認したデータ修正として扱う。
アプリ・Workerの機能追加はminor更新を基本とし、PR作成時にその時点のバージョンから判断する。

旧Worker・旧アプリは`ASSIGNED`を全員参加として扱い得る。指定予定が作られた後に、その旧版へ単純ロールバックしない。
復旧版でも`ASSIGNED`の読み取りと出欠連絡禁止を残し、新規作成・指定変更だけ停止できるようにする。
テーブルは通常の復旧では削除しない。ローカル・開発DBで移行と削除CASCADEの挙動を事前検証する。

## 10. TDDで確認する受け入れ条件

- 3方式を正しく読み書きし、不正値を新規登録できない。
- 作成時に0人・1人・複数人を指定でき、OB・OG・仮入部も含められる。
- 参加者のID正規化・重複排除・不在ID・上限超過を検証する。
- 予定と参加者の保存途中で失敗すると、どちらも残らない。
- 作成者だけが追加・解除でき、一般部員・役職者・指定本人でも他人の予定は変更できない。
- 本人ID・所有者ID・指定者IDの偽装、直接Worker呼び出し経路の権限抜けを防ぐ。
- 作成後は全方式の変更を拒否する。同値・省略・一般項目変更は成功する。
- 同時編集・再送・0人化で参加者が消失・重複せず、古いrevisionの別集合は409になる。
- 指定済み本人の参加登録・辞退・出欠連絡をUIとAPIの両方で拒否する。
- 全ログイン利用者が予定と指定者名を閲覧でき、指定されていない人に予定が隠れない。
- 参加登録・欠席者・当日の出席確認に指定情報が混入しない。
- 名前変更・部員削除・無効化後も指定情報が消えず、表示名の予備値で読める。
- 予定削除で指定情報も消える。別予定の指定には影響しない。
- 当日通知とBOTで指定者全員を掲載し、0人・多数・OB・OG・同名を正しく扱う。
- 既存2方式の通知、次回部会、開始終了時刻保存、ホーム表示に回帰がない。
- モバイル・ダークモード・キーボード操作・検索・保存失敗時の入力保持を確認する。
- キャッシュ復元・別画面遷移・保存直後でも方式と指定者が整合する。
