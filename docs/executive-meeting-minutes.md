# 幹部役員会議の議事録

## 概要

部長・副部長・会計だけが利用できる議事録機能。NBポータルのCloudflare Workerと既存D1を使い、新しい外部データベースは追加しない。議事録は作成直後から幹部全員に表示され、作成者だけが編集・削除・Discord送信できる。

## 画面と権限

- PCサイドバーとモバイルDockに「議事録」を表示する。Dockは既存項目を外さず7項目とし、「その他」には入れない。
- 表示対象ロールは`HEAD`、`SUB_HEAD`、`ACCOUNTANT`。Workerでも現役メンバーと役職を検証する。
- 一覧は開催日の新しい順。検索対象は会議情報・Agenda名と本文・その他欄。出席者名は検索しない。
- 詳細は閲覧モード、編集は専用ページ。作成者以外は閲覧のみ。
- Agendaは上下ボタンで並べ替え、追加・編集・削除できる。最後の1件は削除できない。
- 出席者候補は現役幹部。作成者は出席者に自動で含める。学籍番号を保存し、表示名は`members`から都度取得する。
- 記録者は作成者。編集履歴・公開状態・確定状態は持たず、保存内容をそのまま最新内容とする。
- 詳細閲覧中は5秒間隔で`updated_at`を確認し、更新があった場合だけ本文を取り直す。

## 自動保存

編集から1秒入力が止まった時点で保存する。保存表示は画面下部に置く。通信失敗時は数回再試行し、失敗状態を表示する。ページ内リンクで移動するときは保存完了を待ち、復旧しない場合は未保存のまま移動するか確認する。

## 採番

会議名は`第{回数}回 幹部役員会議`。部長が変わると新しい採番シリーズを作り、第1回から開始する。手動リセットも新シリーズを作る。手動リセットは幹部の誰でも実行でき、確認ダイアログを表示する。

各シリーズで現存する最大番号に1を加える。最新回を削除した場合は、その番号を次回に再利用する。途中番号を削除しても後続番号を詰めない。既存データの代替わり履歴は復元できないため、初回のシリーズは実装後に登録されている部長を基準とする。

## Discord送信

送信先は既存スレッド。Embedを先に送り、成功したときだけ本文を送る。本文は2,000文字を超える場合、Unicode文字単位で先頭1,995文字と`...`を送る。Embedと本文の状態・試行回数・送信時刻・エラーを別々に保存する。部分失敗は失敗した側だけ再送し、再送内容はその時点の最新内容を使う。完全送信後の編集はDiscord投稿へ反映しない。

設定はNext.jsサーバー環境変数に置き、Preview/DevelopmentとProductionでは同じ名前に異なる値を登録する。値がない場合は送信エラーとし、他機能のWebhookへフォールバックしない。

| 変数                                    | 用途                   |
| --------------------------------------- | ---------------------- |
| `DISCORD_EXECUTIVE_MEETING_WEBHOOK_URL` | 専用Webhook URL        |
| `DISCORD_EXECUTIVE_MEETING_THREAD_ID`   | 投稿先の既存スレッドID |

Embedと議事録本文は別メッセージ。本文はコピー操作からも取得できる。議事録を削除してもDiscord側の投稿は削除しない。

## D1

マイグレーション`0015_executive_meetings.sql`を使用する。開催日時は日付と開始時刻のみとし、JSTのローカル文字列で保存する。既存スキーマの`end_time`列は互換性のため残し、新規保存では`NULL`にする。監査・送信時刻はUTC ISO文字列で保存し、画面ではJST表示する。

| テーブル                  | 主な項目                                                                                                                             | 制約・用途                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `meeting_number_series`   | `id`, `department_head_student_number`, `reset_reason`, `created_by`, `created_at`                                                   | 代替わり・手動リセット単位                                |
| `meeting_numbering_state` | `id=1`, `current_series_id`, `observed_head_student_number`, `updated_at`                                                            | 現行シリーズと部長の監視状態                              |
| `executive_meetings`      | `id`, `series_id`, `meeting_number`, 開催日・開始時刻・場所、`attendee_student_numbers_json`, `content_json`, 作成者・更新者・各時刻 | `(series_id, meeting_number)`を一意にする。削除は物理削除 |

`content_json`は`{ "agendas": [{ "id": "...", "title": "...", "body": "..." }], "other": "..." }`。Agenda配列の順番を表示順に使う。通知状態は議事録行にEmbed・本文ごとの状態、開始時刻、送信時刻、試行回数、最終エラーを保存する。履歴テーブルは作らない。

## 運用上の注意

ローカル・Preview・本番それぞれで専用WebhookとスレッドIDの設定が必要。環境設定後にローカルマイグレーションとWorkerテストを実行する。本番D1へのマイグレーション・Workerデプロイは別途承認後に行う。

5秒ポーリングは詳細ページを開いている人数・時間に比例してWorkerリクエストを消費する。常時5人が8時間開いた場合は約28,800リクエスト/日。Cloudflare Free枠の他機能との合算を本番運用後に確認する。
