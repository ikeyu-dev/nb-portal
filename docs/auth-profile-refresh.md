# 部員プロフィール再同期の重複取得対策（#208）

## 目的と範囲

同時に届くページ・APIリクエストが、同じ部員情報を繰り返し取得する問題を抑える。
Proxy内の重複と、複数のVercelサーバー間の重複を分けて扱う。

- Proxyで更新したJWTを、後続処理のCookieヘッダーへ引き継ぐ。
- セッション再同期はWorkerの`session-member-profile`を使う。
- 同じ部員の要求を1つのDurable Objectへ集め、処理中の取得と最大5秒間の成功結果を共有する。
- `verify-member`は従来どおり毎回D1を読む。ログイン時と更新操作の権限確認には共有結果を使わない。

## 鮮度と障害時の動作

JWTの同期時刻には、応答を受け取った時刻ではなくD1の読取開始時刻を設定する。
その時刻から60秒を超えたら再同期するため、共有結果の再利用で同期期限は延びない。
新しいプロフィールが取得できなかった場合の既存JWT保持動作は変更しない。
したがって、障害時や部員削除時まで含めた「必ず60秒以内の権限失効」を保証する変更ではない。

Durable Objectには部員ごとの成功結果1件と処理中のPromiseのみを保持する。
永続ストレージには書き込まず、再起動時はD1から取得し直す。不在・失敗はキャッシュしない。
異なる部員を同じObjectへ誤って渡した場合は拒否する。

## 検証基準

- [x] 更新JWTを後続のAuth.jsに渡して再取得を抑える。分割Cookieの縮小・削除にも対応する。
- [x] 共有結果の元の取得時刻から60秒後に再同期する。
- [x] Worker実行環境で8件の要求が1件のD1読取結果を共有する。
- [x] 別部員との分離、5秒での失効、不在・失敗後の再試行を確認する。
- [x] `verify-member`はキャッシュを使わない。
- [ ] 本番で期限超過時と期限内の3並列API取得を実行し、応答時間とCookie更新を確認する。
- [ ] 本番ログで`member_profile_refresh`の`source=d1`が1件となることを確認する。

Workerログには取得単位のランダムな`lookupId`と`source`（`d1` / `inflight` / `cache`）を出す。
識別子・プロフィール・Cookie値は追加ログへ出さない。
HTTP要求数とD1読取数を区別する。別サーバーからWorkerへのHTTP要求自体は残る。
Objectの再起動や5秒を超える要求のずれでは、追加のD1読取が発生し得る。

## 本番反映と復旧

先にWorkerへDurable Objectのbinding・migration・新APIを反映し、その後アプリを反映する。
旧アプリは既存APIを使うため、Workerを先行デプロイしても動作する。
復旧時はアプリを先に戻す。新APIを使うアプリが残っている間はWorkerの新APIを削除しない。
Durable Objectのnamespace削除は通常の復旧に含めない。

Durable Objectsは新たな課金対象になり得るため、本番導入は承認後に行う。
本番検証前の基準値はIssue #208の2026-09-06のコメントに記録済み。
