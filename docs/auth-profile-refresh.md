# 部員プロフィール再同期の重複取得対策（#208）

## 目的と範囲

同時に届くページ・APIリクエストが、同じ部員情報を繰り返し取得する問題を抑える。
Proxy内の重複と、複数のVercelサーバー間の重複を分けて扱う。

- Proxyで更新したJWTを、後続処理のCookieヘッダーへ引き継ぐ。
- セッション再同期はWorkerの`session-member-profile`を使う。
- 同じ部員の要求を1つのDurable Objectへ集め、処理中の取得と最大5秒間の成功結果を共有する。
- `verify-member`自体は従来どおり毎回D1を読む。ただし、更新操作が常にこのAPIを呼ぶわけではない。
  たとえば次回部会の更新・送信APIはセッションの権限を優先し、権限がない場合のみ再取得する。

## 鮮度と障害時の動作

JWTの同期時刻には、応答を受け取った時刻ではなくD1の読取開始時刻を設定する。
その時刻から60秒を超えたら再同期するため、共有結果の再利用で同期期限は延びない。
新しいプロフィールが取得できなかった場合の既存JWT保持動作は変更しない。
したがって、障害時や部員削除時まで含めた「必ず60秒以内の権限失効」を保証する変更ではない。

Durable Objectには部員ごとの成功結果1件と処理中のPromiseのみを保持する。
永続ストレージには書き込まず、再起動時はD1から取得し直す。不在・失敗はキャッシュしない。
異なる部員を同じObjectへ誤って渡した場合は拒否する。

## 検証基準

- [x] 更新JWTを後続のAuth.jsに渡して再取得を抑える。分割Cookieの縮小・削除にも対応する。
- [x] 共有結果の元の取得時刻から60秒後に再同期する。
- [x] Worker実行環境で8件の要求が1件のD1読取結果を共有する。
- [x] 別部員との分離、5秒での失効、不在・失敗後の再試行を確認する。
- [x] `verify-member`はキャッシュを使わない。
- [ ] 本番で期限超過時と期限内の3並列API取得を実行し、応答時間とCookie更新を確認する。
- [ ] 本番ログで`member_profile_refresh`の`source=d1`が1件となることを確認する。

Workerログには取得単位のランダムな`lookupId`と`source`（`d1` / `inflight` / `cache`）を出す。
識別子・プロフィール・Cookie値は追加ログへ出さない。
HTTP要求数とD1読取数を区別する。別サーバーからWorkerへのHTTP要求自体は残る。
Objectの再起動や5秒を超える要求のずれでは、追加のD1読取が発生し得る。

## 本番反映と復旧

先にWorkerへDurable Objectのbinding・migration・新APIを反映し、その後アプリを反映する。
旧アプリは既存APIを使うため、Workerを先行デプロイしても動作する。
復旧時はアプリを先に戻す。新APIを使うアプリが残っている間はWorkerの新APIを削除しない。
Durable Objectのnamespace削除は通常の復旧に含めない。

Durable Objectsは新たな課金対象になり得るため、本番導入は承認後に行う。
本番検証前の基準値はIssue #208の2026-09-06のコメントに記録済み。

## 再同期の待ち時間への対応（2026-09-28）

Issue #208の計画を段階的に実装する。第1段階は計測と失敗の分類であり、待ち時間の短縮そのものはまだ実装していない。

- [x] 部員不在、HTTPエラー、不正な応答、通信失敗、設定不足を取得結果で区別する。
- [x] HTTPエラー本文に成功情報が含まれていてもセッションに採用しない。
- [x] 同一プロセスの重複排除後、実際に行う取得だけをサンプリングして計測する。
- [x] WorkerのRPC待ち時間とDO内のD1読取時間を記録する。
- [x] 60秒の再同期間隔、Cookieの引き継ぎ、不在・障害時の既存JWT保持を回帰テストで確認する。
- [ ] 本番で計測を一時的に有効にし、区間別の待ち時間を比較する。
- [ ] 期限前更新、タブ間の調整、ログアウト・Cookie応答順序への対策を実装する。
- [ ] 実測を踏まえてタイムアウトを決め、期限超過時の同期処理と合わせて検証する。

### 計測の有効化と読み方

Next.js側の`AUTH_PROFILE_TIMING_SAMPLE_RATE`は未設定・0なら無効。0より大きく1以下の値で取得ごとに抽選する。
たとえば0.1は約10%、1は全取得が対象となる。本番設定の変更は別途行う。
Worker側は既存の取得ログに計測値を追加するため、サンプル率0でもWorkerログは残る。

Next.jsの`member_profile_fetch`にはランダムな`traceId`、用途、結果、HTTPステータス、`totalMs`を記録する。
セッション再同期では同じIDをWorkerへ渡し、`member_profile_refresh`と対応づける。
ログインなどの`verify-member`はNext.js側の総時間のみを記録する。
学籍番号、氏名、権限、Cookie、URL、例外の本文は追加ログに含めない。
WorkerはUUID v4形式のIDだけを受け入れ、任意のヘッダー文字列をそのまま記録しない。

| 項目 | 意味 |
| --- | --- |
| `totalMs` | Next.jsで取得開始からJSONの読取・検証が終わるまで |
| `rpcMs` | WorkerがDOの応答を待った時間。移送・起動・待ち合わせも含む |
| `lookupD1Ms` | 共有された元のD1読取にかかった時間 |
| `d1Ms` | この要求が新規に開始したD1読取時間。共有・キャッシュ利用時は0 |
| `cacheAgeMs` | D1読取開始からWorkerが結果を受け取るまでの経過時間。新規取得でも0とは限らない |

`totalMs - rpcMs`を純粋なネットワーク時間とみなしてはいけない。シリアライズなどの処理も含まれる。
`lookupD1Ms`は再利用された結果にも付くので合計しない。D1取得件数は引き続き`source=d1`で数える。
RPC失敗時は本文を伏せて503を返す。Next.js側ではHTTPエラーとなり、既存JWTは保持される。
タイムアウト時間・認可の有効期間・先行更新の頻度は、この段階では変更しない。
